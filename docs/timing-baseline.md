# Timing baseline

The Core is intentionally kept as a simple in-order educational pipeline.  A
post-route timing report is therefore part of the sign-off evidence rather
than an inferred property of simulation.

## Direct-clock comparison

`rv32_pynq_z2_sync_demo` clocks the Core and BRAM directly from the PYNQ-Z2
125 MHz oscillator (`sys_clk`, 8 ns period).  The current implementation has
the following post-route result on `xc7z020clg400-1`:

| Metric | Result |
|---|---:|
| WNS | −0.796 ns |
| TNS | −90.576 ns |
| Failing setup endpoints | 288 |
| WHS | +0.147 ns |

The critical path starts at the synchronous instruction response register and
crosses the combinational decode, register-file/forwarding, and EXU control
logic.  This image remains useful for comparison, but it is not a timing
sign-off image at 125 MHz.

## Timing-safe LED-only comparison image

`rv32_pynq_z2_sync_mmcm_demo` uses the board's 125 MHz clock only as the MMCM
reference.  `MMCME2_BASE` is configured for

```text
125 MHz × 8 / 12.5 = 80 MHz
```

The Core, instruction ROM, data BRAM, and LED register all use the generated
80 MHz clock.  The post-route result is:

| Metric | Result |
|---|---:|
| Input clock | 125 MHz |
| Generated Core clock | 80 MHz |
| WNS | +0.268 ns |
| TNS | 0 ns |
| Failing setup endpoints | 0 |
| WHS | +0.059 ns |
| Failing hold endpoints | 0 |
| DRC errors | 0 |

The post-route DRC report has no errors.  It contains two `PDRC-138` LUT
packing warnings and the expected PL-only `ZPS7-1` advisory because this
standalone image intentionally does not instantiate PS7; the earlier RAMB18
asynchronous-control advisories remain eliminated.  Reset is captured in the
continuously running 125 MHz domain and passed through an `ASYNC_REG` two-stage
synchronizer in the generated-clock domain.  The XDC false path terminates only
at the first synchronizer register; the second stage and all CPU logic remain
timed.  None of the remaining warnings prevents bitstream generation.  The
board image is generated by the reproducible scripts under `vivado/` and the
`MMCM PYNQ PASS:` XSim test covers both cold start and runtime BTN0 reset.

## RT-Thread Nano / Zmmul board image

The current top, `rv32_pynq_z2_nano`, adds the Nano ROM/RAM, machine timer,
polling UART, LED peripheral, and the four standard `Zmmul` instructions. The
combinational multiply path is intentionally signed off at 50 MHz while the
RV32I-only comparison image above remains an 80 MHz reference. It was
implemented with Vivado 2024.2 for `xc7z020clg400-1` using eight
implementation threads. Its post-route result is regenerated by the checked-
in build script:

| Metric | Result |
|---|---:|
| Input clock | 125 MHz |
| Generated Core clock | 50 MHz |
| WNS | +1.015 ns |
| TNS | 0 ns |
| Failing setup endpoints | 0 |
| WHS | +0.155 ns |
| Failing hold endpoints | 0 |
| LUT | 2359 (4.43%) |
| Flip-flops | 1821 (1.71%) |
| Block RAM tiles | 24 (17.14%) |
| DSP48E1 | 7 (3.18%) |
| DRC errors | 0 |

The reports and bitstream are preserved under
`build/bitstream_pynq_z2_nano/`. Vivado still emits non-fatal DSP input/output
pipelining advisories and the expected PL-only `ZPS7-1` advisory; the timing
report also records RAM inference and missing I/O-delay advisories. These do
not create failing timing endpoints or prevent bitstream generation.
The `PYNQ NANO PASS:` XSim test additionally covers the generated-clock reset,
UART TX, LED MMIO, restart behavior, and active-interface X/Z checks.
